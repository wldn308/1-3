# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 **Cross(+)** 인지 **X** 인지 판별하는 Python 콘솔 프로그램입니다.
NPU가 대량으로 병렬 수행하는 "같은 위치끼리 곱하고 모두 더하기"를 순수 Python 반복문으로 재현하고,
크기별 연산 시간을 측정해 O(N²) 증가를 직접 확인합니다.

- Python 3.8 이상 (3.8.20, 3.12.3, Windows 환경에서 실행 확인)
- 표준 라이브러리(`json`, `time`, `re`, `math`, `os`, `sys`, `argparse`, `unicodedata`, `typing`)만 사용, NumPy / pandas 미사용

---

## 1. 실행 방법

```bash
python main.py                        # 실행 후 메뉴에서 모드 선택
python main.py --data ./other.json    # 다른 경로의 JSON을 분석할 때
```

| 메뉴 | 동작 순서 |
|---|---|
| `1` 사용자 입력(3x3) | 필터 A·B 입력 → 저장 확인 → 패턴 입력 → MAC 연산 → 판정(A / B / 판정 불가) → 3x3 성능 분석 |
| `2` data.json 분석 | 필터 로드 → 패턴 로드·검증 → MAC 연산·판정·PASS/FAIL → 성능 분석(3x3, 5x5, 13x13, 25x25) → 결과 요약 |
| `3` 패턴 생성기(보너스) | N 입력 → N×N Cross·X 생성 → 자기 검증 → 성능 분석 |
| `0` 종료 | |

선택한 모드를 한 번 실행하면 프로그램이 끝납니다.

**data.json 위치**: 기본값은 `main.py`와 같은 폴더의 `data.json`입니다(없으면 현재 작업 폴더에서 찾음).

**모드 1 입력 방법**: 한 줄에 숫자 3개를 공백으로 구분해 입력하고, 3줄을 입력한 뒤 **빈 줄에서 Enter**를 눌러 마칩니다.
첫 줄에 `cross`(또는 `+`)나 `x`를 입력하면 패턴 생성기가 해당 3x3 패턴을 바로 채웁니다.

```
>> 필터 A 입력: 각 줄에 숫자 3개를 공백으로 구분, 3줄 입력 후 빈 줄에서 Enter
  1행 > 0 1 0
  2행 > 1 1 1
  3행 > 0 1 0
  4행 >            ← 빈 줄에서 Enter
```

빈 줄로 입력을 끝내는 이유: 정확히 3줄만 읽으면 4줄을 붙여넣었을 때 4번째 줄이 다음 입력(필터 B)으로 넘어가 버려 행 수 초과를 잡을 수 없습니다. 입력을 모두 받은 뒤 행 수를 세면 초과와 부족을 모두 검출할 수 있습니다.

## 2. 구현 요약

### 2-1. 데이터 구조: `Grid`
- N×N 2차원 리스트를 감싼 클래스입니다. `get(row, col)` / `set(row, col, value)`로 특정 위치를 읽고 쓰며, 범위를 벗어나면 `IndexError`가 발생합니다.
- `Grid.from_rows()`는 JSON·콘솔 데이터를 변환하면서 리스트 여부, 정사각형 여부, 숫자 타입, 유한값(NaN/inf 거부)을 검증합니다. bool과 문자열 `"1"`은 숫자로 인정하지 않습니다.
- 크기 제한이 없어 3×3, 5×5, 13×13, 25×25를 모두 처리합니다.

### 2-2. 라벨 정규화
프로그램 내부에서는 표준 라벨 `Cross`, `X` 두 가지만 사용합니다.

| 원본 표기 | 위치 | 표준 라벨 |
|---|---|---|
| `'+'` | patterns.expected | `Cross` |
| `'x'` | patterns.expected | `X` |
| `'cross'` | filters 키 | `Cross` |
| `'x'` | filters 키 | `X` |

- `normalize_label()`은 `strip().lower()` 후 별칭 표를 조회하므로 `' CROSS '`, `'X'`도 정규화됩니다.
- 별칭 표에 없는 값(예: `'circle'`)은 해당 케이스를 데이터/스키마 FAIL로 처리합니다.
- 정규화가 필요한 이유: 같은 의미를 데이터는 `'+'`/`'x'`, 필터 키는 `'cross'`/`'x'`, 판정 결과는 `Cross`/`X`로 서로 다르게 적습니다. 그대로 비교하면 `"Cross" != "+"`가 되어, 판정은 맞았는데 표기 때문에 FAIL이 납니다. 데이터를 읽는 시점에 한 번만 표준화하면 이후 비교·출력 코드는 표기 차이를 신경 쓰지 않아도 됩니다.

### 2-3. MAC 연산
```python
total = 0.0
for i in range(n):
    for j in range(n):
        total += a[i][j] * b[i][j]
```
- `mac_2d()`: 위 이중 반복문(기본 구현). 크기가 다르면 `SchemaError`.
- `mac_flat()`: (보너스) 1차원 리스트(길이 N²)를 인덱스 하나로 순회. 합산 순서가 같아 `mac_2d()`와 결과가 비트 단위로 동일합니다.

### 2-4. 점수 비교 정책 (epsilon)
- `EPSILON = 1e-9`이며, `abs(score_a - score_b) < EPSILON`이면 동점으로 봅니다. 모드 1은 "판정 불가", 모드 2는 `UNDECIDED`로 표시합니다.
- 동점이 아니면 큰 점수 쪽으로 판정합니다. `UNDECIDED`는 expected(Cross/X)와 같을 수 없으므로 항상 FAIL입니다.
- 결과 요약에서는 비교를 위해 "epsilon 없이 `>`로 비교했다면 어떤 판정이 나왔을지"도 함께 보여 줍니다.

### 2-5. 오류 처리
| 상황 | 처리 |
|---|---|
| 모드 1: 행 수 초과/부족, 열 수 불일치, 숫자 파싱 실패 | 발견한 오류를 모두 안내한 뒤 해당 행렬을 처음부터 다시 입력 |
| 모드 2: 파일 없음 / JSON 문법 오류 | 오류 메시지를 출력하고 분석 중단 (비정상 종료 없음) |
| 모드 2: 키 형식 오류, `input`/`expected` 누락, 알 수 없는 라벨, 비정사각 배열, 숫자가 아닌 값, 키의 N과 실제 크기 불일치, 해당 크기 필터 없음/불완전 | 케이스 단위 FAIL + 원인 메시지, 다음 케이스 계속 진행 |
| 입력 스트림 종료(EOF), Ctrl+C | 안내 후 정상 종료 |

실패는 데이터/스키마, 수치 비교(동점), 판정 불일치 세 범주로 분류해 결과 요약에 집계합니다.

### 2-6. 성능 측정 방식
- `time.perf_counter()`로 MAC 함수 1회 호출 구간만 측정합니다(입력·출력·파일 읽기·1차원 변환은 측정에서 제외).
- 워밍업으로 1회 실행한 뒤, 1회 호출 시간을 **10회 측정해 평균**을 냅니다.
- 3×3은 data.json에 없으므로 패턴 생성기의 Cross 패턴으로 측정하고, 5/13/25는 data.json의 패턴과 Cross 필터로 측정합니다.
- 1회 호출이 1µs 안팎이라 타이머 자체 오차가 섞이며, 실행할 때마다 값이 조금씩 달라집니다.

## 3. 결과 리포트

### 3-1. data.json 실행 결과

| 케이스 | expected | Cross 점수 | X 점수 | 판정 | 결과 | epsilon 없이 `>` 비교 시 |
|---|---|---|---|---|---|---|
| size_5_1 | `x`→X | 0.9 | 0.8999999999999999 | UNDECIDED | **FAIL** | Cross (오판) |
| size_5_2 | `+`→Cross | 8.9 | 0.1 | Cross | PASS | Cross |
| size_13_1 | `x`→X | 0.3 | 14.700000000000008 | X | PASS | X |
| size_13_2 | `+`→Cross | 7.499999999999997 | 7.5 | UNDECIDED | **FAIL** | X (오판) |
| size_25_1 | `x`→X | 4.9 | 4.899999999999999 | UNDECIDED | **FAIL** | Cross (오판) |
| size_25_2 | `+`→Cross | 52.9 | 0.1 | Cross | PASS | Cross |

**총 6건 / 통과 3건 / 실패 3건.** 실패 3건은 모두 "수치 비교(동점)" 범주이고, 데이터/스키마 실패와 판정 불일치는 0건입니다.

### 3-2. FAIL 원인 분석

1. **스키마·라벨 문제가 아니다**: 세 크기의 필터가 모두 `cross`/`x` 두 종류로 정상 로드되었고, 모든 패턴의 키 N과 실제 input 크기가 일치했습니다. expected의 `'+'`/`'x'`도 정규화 후 `Cross`/`X`로 비교했으므로 표기 차이로 생긴 FAIL은 없습니다.
2. **로직 문제가 아니다**: 같은 MAC 함수가 나머지 3건(size_5_2, size_13_1, size_25_2)은 큰 점수 차로 정확히 판정했습니다. 2D/1D 두 구현의 결과도 같고, 패턴 생성기 자기 검증(Cross→Cross, X→X)도 통과합니다.
3. **실제 원인은 필터 가중치 때문에 생긴 "수학적으로 정확한 동점"이다**: 실패 케이스를 손으로 계산하면 두 점수가 정확히 같습니다.
   - size_5_1 (X 패턴): Cross 필터와는 중앙 1칸만 겹치고 중앙 가중치가 0.9 → **0.9**. X 필터는 대각선 9칸 × 0.1 → **0.9**.
   - size_13_2 (Cross 패턴): Cross 필터는 25칸 × 0.3 → **7.5**. X 필터와는 중앙 1칸만 겹치고 중앙 가중치가 7.5 → **7.5**.
   - size_25_1 (X 패턴): Cross 필터와는 중앙 1칸(가중치 4.9)만 겹침 → **4.9**. X 필터는 49칸 × 0.1 → **4.9**.

   즉 "반대 모양 필터의 중앙 가중치 = 정답 필터 가중치의 합"이 되도록 만들어져 있어서, 두 필터가 이 패턴을 구별하지 못합니다.
4. **부동소수점이 동점을 가린다**: 0.1, 0.3 같은 값은 2진수로 정확히 표현되지 않아 여러 번 더하면 오차가 쌓입니다(0.1을 9번 더하면 0.8999999999999999). 그래서 수학적 동점이 1e-16 ~ 1e-15 크기의 "가짜 차이"로 바뀝니다.
5. **epsilon이 없으면 오히려 더 나쁘다**: 단순 `>` 비교로는 세 건 모두 반대 라벨로 오판합니다(위 표 마지막 열). 그러면 "로직이 모양을 잘못 인식했다"처럼 보여 진단이 엇나갑니다. epsilon(1e-9)을 적용하면 오차(최대 2.7e-15)는 동점으로 흡수되고, 실제로 의미 있는 차이(정상 케이스는 8.8 ~ 52.8)는 그대로 판정됩니다. 결과는 여전히 FAIL이지만 원인이 "동점(판정 불가)"으로 정확히 드러납니다.
6. **개선 방향**: 원인이 코드가 아니라 데이터(필터 가중치)에 있으므로, 테스트를 통과시키려고 비교 로직을 바꾸는 것은 잘못된 수정입니다. 필터 중앙 가중치를 조정해 정답 필터 점수가 확실히 크도록 하거나, 동점일 때의 처리 정책을 따로 정하는 것이 올바른 개선입니다. 동점 기준(1e-9)은 요구사항의 권장 기준을 그대로 유지했습니다.

### 3-3. 성능 분석과 O(N²) 근거

측정 환경: Windows, Python 【3.15.2】 / MAC 1회 호출 × 10회 측정 평균

| 크기 | 연산 횟수(N²) | 평균 시간(ms) | 원소당 시간(ns) | 3x3 대비 |
|---|---|---|---|---|
| 3×3 | 9 | 0.00051 | 56.7 | 1.0x |
| 5×5 | 25 | 0.00083 | 33.2 | 1.6x |
| 13×13 | 169 | 0.00448 | 26.5 | 8.8x |
| 25×25 | 625 | 0.01549 | 24.8 | 30.4x |

- MAC은 N×N 각 칸마다 곱셈 1번, 덧셈 1번을 한 번씩 하므로 연산 횟수는 **N²**이고, 시간 복잡도는 **O(N²)**입니다. 한 변 N이 2배가 되면 연산은 4배가 됩니다.
- 13×13 → 25×25에서 연산 횟수는 3.7배, 측정 시간은 3.5배 늘어 거의 비례합니다.
- 3×3 → 25×25 전체로 보면 연산은 69.4배인데 시간은 30.4배에 그칩니다. 함수 호출, `range` 생성처럼 **N과 무관한 고정 비용**이 작은 N에서 큰 비중을 차지하기 때문입니다. 원소당 시간이 56.7ns에서 줄어들다가 13×13(26.5ns) 이후로는 25×25(24.8ns)와 거의 같아지는 것이 그 근거이며, N이 커질수록 시간 ≈ (원소당 시간) × N²가 됩니다.
- 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 사용하므로 이 N² 증가가 곧바로 연산량 폭증으로 이어집니다. NPU가 수많은 MAC 연산기로 이 작업을 동시에 처리하는 이유가 여기에 있습니다.

### 3-4. (보너스) 1차원 배열 최적화 결과

| 크기 | 2D a[i][j] (ms) | 1D a[k] (ms) | 개선율 |
|---|---|---|---|
| 3×3 | 0.00051 | 0.00030 | +41.2% |
| 5×5 | 0.00083 | 0.00057 | +31.3% |
| 13×13 | 0.00448 | 0.00270 | +39.7% |
| 25×25 | 0.01549 | 0.00953 | +38.5% |

- 1차원 접근은 매 칸마다 하던 "행 리스트 꺼내기" 단계가 없고 반복문도 하나로 줄어, 모든 크기에서 약 31~41% 빨라졌습니다.
- 시간 복잡도는 둘 다 O(N²)로 같고, 상수 계수만 줄었습니다. Python 리스트는 C 배열처럼 값이 메모리에 연속으로 놓이지 않으므로, 개선의 주된 이유는 캐시 효과보다 인터프리터가 실행하는 명령 수 감소입니다.

## 4. 재현성 체크리스트

| 시나리오 | 기대 동작 |
|---|---|
| 모드 1: 필터 A=`0 1 0 / 1 1 1 / 0 1 0`, B=`1 0 1 / 0 1 0 / 1 0 1`, 패턴=`1 0 1 / 0 1 0 / 1 0 1` | A 1.0 / B 5.0 / 판정 B / 연산 시간 출력 |
| 모드 1: 필터 A=`0.1 0.1 0.1 / 0 0 0 / 0 0 0`, B=`0 0 0 / 0 0 0 / 0 0 0.3`, 패턴=`1 1 1 / 0 0 0 / 0 0 1` | A 0.30000000000000004 / B 0.3 → 판정 불가 |
| 모드 1: 4줄 입력, 2줄 입력, `1 1`(열 부족), `0 a 1`(숫자 아님) | 오류 목록 안내 후 해당 행렬 재입력 |
| 모드 2: 제공된 data.json | 총 6 / 통과 3 / 실패 3, 실패 사유는 모두 동점 |
| 모드 2: 크기 불일치·라벨 오류·필드 누락 등이 섞인 JSON | 케이스별 FAIL + 원인 메시지, 프로그램은 끝까지 실행 |
| 모드 2: 없는 파일 / 문법이 깨진 JSON | 오류 안내 후 정상 종료 |
